# Course Material RAG Service

A FastAPI service that accepts course-material metadata, lets the frontend upload
files directly to S3-compatible storage, and then chunks and embeds uploaded files
for semantic search in Qdrant.

Supported document types are PDF, DOCX, TXT, and Markdown.

## Current flow

```text
Frontend                 RAG API                PostgreSQL       S3        Qdrant
   |                         |                       |             |            |
   |-- request upload URL -->|                       |             |            |
   |                         |-- save material ---->|             |            |
   |                         |   awaiting_upload     |             |            |
   |<-- material ID + -------|                       |             |            |
   |    presigned PUT URL    |                       |             |            |
   |                                                               |            |
   |-- PUT file directly ----------------------------------------->|            |
   |                                                               |            |
   |-- status: uploaded ---->|                       |             |            |
   |                         |-- verify size and download -------->|            |
   |                         |-- status: processing ->|            |            |
   |<-- status: processing --|                       |             |            |
   |                         |-- extract and chunk file             |            |
   |                         |-- request embeddings                              |
   |                         |-- store vectors --------------------------------->|
   |                         |-- status: completed ->|                           |
   |                                                               |            |
   |-- poll material status ->|                                    |            |
   |<-- completed or failed --|                                    |            |
```

If the direct S3 upload fails, the frontend reports `failed` or `upload_failed`.
The backend then deletes the PostgreSQL record instead of processing it.

```text
awaiting_upload -- uploaded ------> processing -- success --> completed
        |                               |
        |                               +-- processing error --> failed
        |
        +-- failed/upload_failed --> PostgreSQL record deleted
```

The `uploaded` callback is idempotent while a material is processing or completed.
Before processing starts, the backend confirms that the object exists, is not empty,
and does not exceed `MAX_UPLOAD_SIZE_MB`.

## Stored course-material data

PostgreSQL stores one `course_materials` record with only these fields:

| Field | Description |
|---|---|
| `id` | Generated UUIDv4 course-material ID |
| `course_id` | Owning course UUIDv4 |
| `filename` | Sanitized original filename |
| `status` | `awaiting_upload`, `processing`, `completed`, or `failed` |
| `s3_bucket` | Configured course-material bucket |
| `s3_object_key` | Unique object key generated by the backend |

There is one `CourseMaterial` model for both application and persistence use. Chunk
IDs, timestamps, content type, chunk count, and processing errors are not persisted.

Qdrant stores each chunk with its generated point ID and this payload metadata:
`course_material_id`, `document_id`, `course_id`, `filename`, and `chunk_index`.

## Upload API flow

### 1. Request a presigned upload URL

```http
POST /api/v1/course-material/create_presigned
Content-Type: application/json

{
  "course_id": "d87cecc2-e224-4e91-aeef-8c4773452674",
  "filename": "week-01.pdf"
}
```

Example response:

```json
{
  "course_material_id": "10a7de1e-55f5-43b7-8208-c152ef77a5b5",
  "presigned_url": "http://localhost:8333/course-materials/...?X-Amz-Signature=...",
  "object_key": "d87cecc2-e224-4e91-aeef-8c4773452674/10a7de1e-55f5-43b7-8208-c152ef77a5b5.pdf",
  "expires_in": 900
}
```

The backend creates the PostgreSQL record before returning the URL. If presigning
fails, that record is cleaned up.

### 2. Upload directly to S3

The API server does not receive the file upload:

```bash
curl -X PUT "$PRESIGNED_URL" --upload-file ./week-01.pdf
```

The service configures bucket CORS using `CORS_ORIGINS` so browser clients can use
the presigned PUT URL.

### 3. Report the upload result

For a successful S3 upload:

```http
POST /api/v1/course-material/10a7de1e-55f5-43b7-8208-c152ef77a5b5/upload-status
Content-Type: application/json

{
  "status": "uploaded"
}
```

The response is returned after the backend verifies and downloads the S3 object,
and background chunking and embedding have started:

```json
{
  "course_material_id": "10a7de1e-55f5-43b7-8208-c152ef77a5b5",
  "status": "processing"
}
```

For a failed S3 upload, send either accepted failure value:

```json
{"status": "failed"}
```

```json
{"status": "upload_failed"}
```

The response `status` field is `deleted`, and the PostgreSQL record no longer exists.

### 4. Poll processing status

```http
GET /api/v1/course-material/10a7de1e-55f5-43b7-8208-c152ef77a5b5/status
```

```json
{
  "id": "10a7de1e-55f5-43b7-8208-c152ef77a5b5",
  "status": "completed"
}
```

Processing failures retain the record with `status: "failed"`. Partial vectors are
removed from Qdrant. Processing interrupted by an application restart is also
marked failed.

## Other endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Check PostgreSQL, S3, and Qdrant readiness |
| `GET` | `/api/v1/course-material` | List materials; supports `offset`, `limit`, and `course_id` |
| `GET` | `/api/v1/course-material/{id}` | Read one course-material record |
| `POST` | `/api/v1/search` | Search embedded chunks, optionally filtered by course |

Search example:

```bash
curl -X POST http://localhost:8000/api/v1/search \
  -H 'Content-Type: application/json' \
  -d '{
    "query":"How does photosynthesis produce chemical energy?",
    "course_id":"d87cecc2-e224-4e91-aeef-8c4773452674",
    "k":5,
    "score_threshold":0.4
  }'
```

If `API_KEY` is configured, all `/api/v1` requests must include:

```http
X-API-Key: your-api-key
```

The health endpoint remains unauthenticated. Course-material, health, and search
routes are implemented in separate controller modules.

## Run with Docker Compose

Docker Compose starts:

- the FastAPI application;
- PostgreSQL;
- Qdrant;
- SeaweedFS with its S3-compatible API.

The embedding model server is external and must be reachable through
`EMBEDDINGS_URL`. If it is another container, connect it to the `rubric-rag_default`
network with the DNS name used in that URL.

```bash
cp .env.example .env
docker compose up --build -d
docker compose ps
```

Available local endpoints with the default ports:

- API and Swagger UI: <http://localhost:8000/docs>
- Health: <http://localhost:8000/health>
- Qdrant dashboard: <http://localhost:6333/dashboard>
- SeaweedFS S3 endpoint: <http://localhost:8333>

Important configuration:

- `API_KEY` and `CORS_ORIGINS`
- `DATABASE_URL` or the Compose PostgreSQL variables
- `S3_PUBLIC_ENDPOINT_URL`
- `S3_COURSE_MATERIALS_BUCKET`
- `S3_PRESIGNED_URL_EXPIRY_SECONDS`
- `QDRANT_COLLECTION`
- `EMBEDDINGS_URL`, `EMBEDDINGS_MODEL`, and `EMBEDDINGS_DIMENSION`
- `CHUNK_SIZE`, `CHUNK_OVERLAP`, and `MAX_UPLOAD_SIZE_MB`

## Verification

```bash
make lint
make test
```

The old rubric upload API is no longer exposed. The legacy `rubrics` PostgreSQL
table is left untouched to avoid destructive data loss, but this service does not
read from or write to it.
